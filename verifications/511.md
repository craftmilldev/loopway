# Verification for PR 511: loopway 2.0 slice 6, threads that create issues and PRs

This PR adds the MCP tools `create_issue(repo, title, body)` and `create_pr(repo, head, base, title, body)`. They act as `loopway-bot`, put the thread's marker in what they open, and record it in the thread's `sent`. A subject a thread creates joins that thread, and every bot that wants its kind starts a thread for it. Everything below ran on 2026-11-10, on a Mac, on code from this branch (built CLI, `node packages/cli/dist/index.js`, from a scratch directory with a clone of `craftmilldev/loopway-sandbox` and `.loopway/dev.md` and `.loopway/review.md` as in the issue, both `model: sonnet`).

**Bottom line:** steps 1 to 6 of the issue ran against the sandbox with the real `claude`, the real MCP server and the bot token. The dev thread created an issue and a PR, tracked both, and a second dev thread and a review thread started and answered. Closing and merging closed the threads as the rules say, and a restart made no new threads. One thing was not seen live: the thread view's "created by this thread" line (a test covers it).

New tests:

- `rules.test.ts`, "a subject a thread created": the `created` event gives a `track` action plus a thread for every bot that wants the kind (the creator's own bot included, with the creation as its first update); nothing when the thread already tracks it; a closed maker is not given the subject but the new threads still start; discovery's `new` with a thread's marker in its text is read as created by that thread, and one with an unknown marker, or a closed thread's, is an ordinary new subject; the maker stays open until its created subjects close too.
- `threads.test.ts`: the actions applied and written to disk (the `created` flag, the new threads' queues); the marker match when discovery finds the subject first (and the poller does not keep the text); a subject the poller was told about gets no second thread when discovery sees it; closing.
- `sessions.test.ts`: both tools post with the marker, record `sent` (`issue` or `pull_request`, with the new subject), log, and tell loopway; they count as the turn's message; GitHub's refusal is logged and not recorded; a repo the bot does not read, or an unknown thread, is refused before anything is opened.
- `github.test.ts`: the POSTs to `/repos/o/r/issues` and `/repos/o/r/pulls` and the `Made` they return.
- `claude.test.ts`: both tools over the MCP server (listing, results, errors), and the whole loop with the fake `claude` (`open` mode in `test/fake-claude.mjs`): a dev thread opens an issue and a PR, tracks both, a dev and a review thread start and run with the creation as their news, the marker is in everything opened, and a later discovery by `loopway-bot` makes no new thread.
- `tui.test.tsx`: the thread view marks a created subject, and filtering by a created PR shows both the dev and the review thread.

- **The sandbox is shared.** Other loopway instances (other agents' checkouts) were reading the same repo and the same author at the same time, and answered my issues (a comment by thread `3b8c63db` on issue 19 is not from my run), and my `loopway` opened threads for theirs (issues 21 and 24 are not mine; my threads `85a232c7` and `c1eff0a7` ran on them and the bot commented there). The `dev` bot on 19 therefore also took part in a short back and forth of comments with the other instance until 19 closed.
