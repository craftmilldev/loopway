# Verification for PR 500: loopway 2.0 slice 4, the TUI

A bare `loopway` in a terminal opens a TUI on the same poller; `--no-tui`, `--json` and output that isn't a terminal keep the plain log. Everything below ran on 2026-11-10, on a Mac, on code from this branch, against `craftmilldev/loopway-sandbox` (issue #2 and PR #3, both titled `[#500] ...`, both closed again, the branch deleted).

**Bottom line:** steps 1 to 6 of the issue ran live. Two things could not be seen live because slice 3 is not merged: a real session status and a real session log. The session shows `no session yet`, and for the log I wrote `threads/<id>.log` by hand to show the TUI reads it.

## Automated

| Check                  | Result                                              |
| ---------------------- | --------------------------------------------------- |
| `npm test`             | 83 tests in cli (13 new, `tui.test.tsx`), 16 in web |
| `npm run typecheck`    | clean                                               |
| `npm run lint`         | clean                                               |
| `npm run format:check` | clean                                               |

`tui.test.tsx` uses `ink-testing-library` over plain thread objects, no network. It covers: the main view's row (bot, status, session, pending, time, subjects), the poller line at the bottom, the empty list, selection by id surviving list changes, and refresh; the closed window (3 days, judged by latest message, after the open ones, dimmed); the thread view (subjects, session, pending, sent, `no session yet`, `no log yet`, opening with Enter or right arrow, back with left arrow or Esc, the log following output until PgUp and following again on End); and the subject filter (header, only threads holding the subject, Esc clears, filter kept when opening a thread from the filtered view).

## Live

The TUI ran in a pseudo-terminal (100x30) driven by a script that sends keys and records the screen as text. Bot files pointed `dev` (`on: issue`) and `review` (`on: pull_request`) at the sandbox, from a scratch directory outside the checkout, with a throwaway `LOOPWAY_HOME`.

### 1. It opens

```
loopway · 0 threads
No threads yet.
waiting for the poller
↑/↓ move · enter open · esc clear filter · q quit
```

### 2. Open an issue, comment on it

```

▸ dev      open   no session yet  0 pending 2026-11-10 16:04 craftmilldev/loopway-sandbox#2
2026-11-10 16:04 thread opened d3981b30 dev craftmilldev/loopway-sandbox#2
```

After a comment the pending count went up:

```
▸ dev      open   no session yet  1 pending 2026-11-10 16:04 craftmilldev/loopway-sandbox#2
2026-11-10 16:04 queued craftmilldev/loopway-sandbox#2 comment -> d3981b30
```

### 4. Open a PR saying `Closes #2`, filter by it

The review thread appeared. loopway 2.0 does not yet link the PR to the issue's thread, so the dev thread holds #2 only and the review thread holds #3 only:

```
loopway · 2 threads
▸ dev      open   no session yet  1 pending 2026-11-10 16:04 craftmilldev/loopway-sandbox#2
  review   open   no session yet  0 pending 2026-11-10 16:06 craftmilldev/loopway-sandbox#3
```

In the review thread, Enter on the PR subject filters the main view; the filter is in the header. Esc clears it:

```
loopway · 1 threads · filter craftmilldev/loopway-sandbox#3 (esc clears)
▸ review   open   no session yet  0 pending 2026-11-10 16:06 craftmilldev/loopway-sandbox#3
```

```
loopway · 2 threads
  dev      open   no session yet  1 pending 2026-11-10 16:04 craftmilldev/loopway-sandbox#2
▸ review   open   no session yet  0 pending 2026-11-10 16:06 craftmilldev/loopway-sandbox#3
```

Because of that, the filter here shows one thread. With a subject on two threads it shows both; that is in the tests.

### 5. Close the issue

I closed the issue and the PR. Both threads moved to `closed` and stayed listed (dimming is not visible in a text capture; the test checks the dim attribute):

```
loopway · 2 threads
  dev      closed no session yet  2 pending 2026-11-10 16:08 craftmilldev/loopway-sandbox#2
▸ review   closed no session yet  1 pending 2026-11-10 16:08 craftmilldev/loopway-sandbox#3
```

### 6. Quit, and the plain log

`q` quit the TUI and the process exited with it (the poller stopped). `loopway threads` afterwards listed both closed threads. `loopway --no-tui`, and `loopway` with stdout redirected, both printed the plain log:

```
loopway 2.0.0-alpha: watching craftmilldev/loopway-sandbox for mcwhittemore
2026-11-10 16:10 update craftmilldev/loopway-sandbox#2 comment by mcwhittemore
```

(Those runs also printed a `new` line and a `thread opened` line for sandbox issue #4, which another agent opened during the run.)
