# Verification for PR 553: Update loopway itself from the latest release, on by default

Run on 2026-11-16 with the CLI built from this branch (`2.0.1`), on macOS, Node 22. `claude` was not involved. The sandbox is `craftmilldev/loopway-sandbox`, from `npm run init-scratch -- --reset`. I used `gh` auth for GitHub, and a temp `LOOPWAY_HOME` with no bot token, so sessions were off.

The issue has no "How to test it" section, so these steps are mine.

**Bottom line:** the startup update, the update while running, and both off switches passed live against the real latest release (`cli-v2.0.0`). Not run live: updating while a session run is in flight, and the TUI hand-off (both are unit-tested only, see the last section).

How the live runs were set up: I packed this branch's CLI labelled `2.0.0-rc.0` (older than the real `2.0.0`, which is the latest release) and installed it with `npm install -g` into a temp prefix (`npm_config_prefix`), so nothing on the machine's real install was touched. The self-update then downloaded the real `cli-v2.0.0` release tarball from GitHub into that prefix.

## Live, in craftmilldev/loopway-sandbox

**Update at start** (installed `2.0.0-rc.0`, `auto_update` unset):
```
loopway 2.0.0-rc.0: updating to 2.0.0...
loopway 2.0.0: watching craftmilldev/loopway-sandbox for loopway-bot
```
`loopway --version` printed `2.0.0` afterwards.

**Off with `"auto_update": false` in config.json**, and **off with `LOOPWAY_NO_UPDATE=1`** (each from a fresh `2.0.0-rc.0`):
```
loopway 2.0.0-rc.0: watching craftmilldev/loopway-sandbox for loopway-bot
```
`--version` stayed `2.0.0-rc.0` in both.

**Update while running** (started with `LOOPWAY_UPDATED=2.0.0-rc.0`, which skips the start-up check; 14:55:58 to 15:06:28 UTC, checked at the 10-minute mark):
```
loopway 2.0.0-rc.0: watching craftmilldev/loopway-sandbox for loopway-bot
loopway 2.0.0 is out: finishing the runs in flight, then updating
loopway 2.0.0: watching craftmilldev/loopway-sandbox for loopway-bot
```
`--version` was then `2.0.0`. This Node is 22.13, which has no `process.execve`, so the restart took the fallback: pid 16661 stayed as the parent waiting on a child (pid 17906) that runs the new version. The in-place `execve` hand-off was not exercised live (only its environment is unit-tested); on Node 22.15+ it replaces the process instead, and each update on 22.13 adds one waiting parent.

I opened no issues, PRs or branches in the sandbox, so there was nothing there to close.

## What I did not check, and what else happened

- Live runs were against the real `cli-v2.0.0` release, not a faked one; a failed install and a retry of the same release were not run live.
- With no bot token there were no sessions, so a run in flight being waited for is covered only by the `drain` unit test.
- The TUI path (`showTui` unmounting on update, then re-exec) was not run; `--no-tui` was used for all live runs.
- The failure paths (download or install fails) are unit-tested only.
- `process.execve` in place (Node 22.15+) was not run live; see above.
- A newer release than `2.0.0` doesn't exist, so the live runs used an older pre-release as the installed copy. The installed copy is a pre-release only in its package.json label; the code is this branch's.
- Cleanup: the update-while-running process was still alive after my first `kill -INT` (it was the waiting parent), so I stopped both pids with `kill -INT` afterwards; removed the temp prefix and home in `/tmp`.
