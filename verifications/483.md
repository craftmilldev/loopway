# Verification for PR 483: loopway 1.0

This PR takes loopway from 0.4 to 1.0: one inbox per user, read by your own code. Everything below ran on 2026-11-04 and 2026-11-05, on a Mac, on code from this branch.

**Bottom line:** it works end to end on a real server, real Postgres, real CLI processes and a real Claude session. Three adversarial reviewers found real bugs, and those are fixed. Nothing has touched production, a deployed Vercel function, a real CLI release or a live sender, so the first run of those is the merge itself. The [merge runbook](#merge-runbook) covers that.

### The migration, on data the real 0.x app wrote

I ran `origin/main`'s server and CLI, and used them to make two users, a shared org, inboxes, test messages and bots, plus a user with no org. Then I ran this branch's `scripts/migrate.ts` on that database.

- `040_v1` applied, and a second run was a no-op.
- Usernames moved onto `users`; the user with no org got null.
- Every other old table, and the functions that served them, went. Only `users`, `login_codes`, `sources`, `messages`, `api_tokens` and `schema_migrations` remain.
- **There is no way back but the backup.** Migrating drops the old deployment's tables, so it can't serve from that moment, and rollback means restoring. An earlier version of this PR kept them; Matthew chose to drop them here, since the bots stop anyway and nobody else uses loopway.
- `packages/web/test/migrate-existing-data.test.ts` asserts the same, and the release reviewer separately applied an earlier version of this migration to 200k messages and awkward users, and injected a mid-migration failure, which rolled back cleanly.

### Real payloads and a real client

- **12 kinds of real GitHub delivery** (`push`, `pull_request`, `pull_request_review`, `check_run`, `workflow_run` and others), taken from the org webhook's delivery log and posted to the inbox. All returned `202` and mapped to the right type, subject and source. GitHub's log doesn't keep the signed bytes, so I re-signed them with a test secret: this proves the payloads, not GitHub's own signature.
- **Real Claude as the MCP client.** `claude -p` with this server in its MCP config pushed a message and pulled messages, using a real token. On the final code it pushed, then ran out of the turn limit I'd set while paging, so `pull_messages` is proven by the earlier run and by `mcp.test.ts`.
- **A real slow insert.** `api.test.ts` holds an insert open in a real transaction while a newer message commits and a reader reads, and the slow one still arrives. Another test blocks an insert on a lock and confirms it fails inside the holdback.

### Adversarial review

Three independent agents each tried to break one area, given the code and not my reasoning. They used their own scratch copies and databases.

**Held up:** 8 concurrent pushers with a real poller throwing at random, about 2000 messages, none lost or out of order. 169 tied rows across limits and filters. 20,000 microsecond round trips. Every route without a token, tenant isolation, secret read-back, forged tokens, SQL injection in filters.

**Found and fixed:**

| Finding | Fix |
| --- | --- |
| A commit slower than the holdback could be lost for good | Inserts time out at 3s, inside the 5s holdback, and the sender retries |
| A refused `--since` destroyed the saved cursor | The server validates it before the cursor is touched |
| A new message could dedupe against an expired, invisible row | An expired row is replaced |
| An unreadable cursor was overwritten with "now" | Only a missing file means a new reader |
| `poll` died if the server was down at startup, and retried a 400 forever | It waits for the server, and gives up on 4xx |
| `read` hung when a reader held a handle | It exits |
| Unauthenticated login lockout | A code out of guesses can be replaced after a minute; see below |
| Unauthenticated requests changed a source's delivery status, and tried every source's body | Only a verified delivery writes status, and a body is only read if a source claims it |
| Terminal escapes from message content reached the terminal | Control characters print as text |
| NUL bytes and bad MCP input caused 500s | Stripped from messages, `400` elsewhere, tool errors in MCP |
| Header probing showed which sources a user has | Nothing but `401` before a signature verifies |
| Linear deliveries could be replayed under new ids | The signed `webhookTimestamp` is enforced |
| Cron did its purge last, with a metric per message | Purge first, one metric per tick |
| The migration destroyed data while the old deployment was serving | Accepted: nobody else uses it. The build bundles first, so a cheap failure can't reach the database |
| Build migrated before bundling | Bundles first |
| `loopway bots run` died with "unknown command" | Removed commands say what happened |

## What I didn't check

### Couldn't do

- **Production data.** I have no production access and didn't try to get any. Row counts, migration time and old oddities are unknown.
- **A deployed Vercel function, or Supabase's pooler.** `vercel.json` only deploys `main`. I also didn't deploy a preview: the build runs migrations, and a preview could point at production's database.
- **A real delivery from GitHub, with its own signature.** That needs a public tunnel to a local server, and the permission system blocked installing one. To do it: run `cloudflared tunnel --url localhost:3000`, add a webhook pointing at it, and ping it.
- **Linear, Vercel, Granola and Resend for real.** Their adapters have tests with signed fixtures, but no live delivery and no real payloads.
- **A real release.** `release-cli.yml` only runs on `main`. Its version logic is read and replayed, not run.
- **Real login email.** The dev server printed the code, so Resend wasn't used.

### Could have done, and didn't

- **Safari and Firefox.** Chrome only.
- **Load.** No measurements on Supabase. A reader polling every 5 seconds is about 17,000 queries a day until it slows down.
- **The 54 deleted test files, one by one.** I judged them by name and imports. One held coverage that still mattered, so others may too.
- **`.claude/skills/verify-read-cursor`.** Another session's model checker for the cursor. It reached the same design independently, but it's untracked, not in this PR, and still points at the old `listMessages`, so it hasn't been run against this code.

### Known gaps, on purpose

Matthew decided these on 2026-11-05.

- **No rate limits or quotas.** Anyone who can sign up can send email to any address (one per address per 10 minutes), store 1 MB messages, and run schedules. The login lockout fix is partial for the same reason: an attacker can still burn each new code, at the cost of emailing the victim. **Decision:** signups stay closed (`SIGNUPS=closed`) until limits exist.
- **GitHub replay.** The signature covers the body, not the event type or delivery id, so someone holding a captured body and signature can replay it under a new id or type. They'd need webhook admin access or a leaked log. Deduping on the body hash could drop real events. **Decision:** accepted as it is.
- **A commit stuck past 5 seconds.** The insert timeout covers the statement, not the commit. A commit that stalls that long can still land behind a reader.
- **Replacing sources.** Every sender's URL changes, and sender-made secrets must be fetched again, so deliveries fail until each is re-pointed.
- **plumbline.** `bin/plumb` and the five bots use `loopway bots`, which is gone. **Decision:** they stop at merge, and nobody else uses or self-hosts loopway, so no one needs warning and no 0.4.8 stepping stone is needed. `craftmill/site` also still describes the old product.

## Merge runbook

1. Confirm `SIGNUPS=closed` is set on production.
2. Take a Supabase backup.
3. Merge. Vercel bundles, then applies `040_v1`, which drops everything but users and login codes. From here the old deployment is down, and the backup is the only way back.
4. Confirm the deploy: `/api/health`, a login, and a webhook.
5. Check that 1.0.0 released: it fires once CI passes on `main`. If CI goes red, 0.x CLIs get a `426` with nothing to update to until it's rerun.
6. Re-register each source and point each sender at the new inbox URL.
