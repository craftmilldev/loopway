# loopway v2

loopway stops running bots and becomes a notification system for them: one inbox per user, read from your own machine. What happens to a message is the reader's business.

## The design

- **No orgs.** A user has one inbox. Orgs can come back if they turn out to be needed.
- **One inbox URL per user.** Senders are told apart by their signature header (`x-hub-signature-256`, `linear-signature`, ...).
- **Registered validations are signature storage.** A user stores signing secrets; there are no event filters, schemas or setup flows. A delivery that matches no stored secret gets a `401` and isn't stored.
- **Everything is a CloudEvent.** The per-sender adapters in `packages/sources` stay, cut down to verifying a delivery and mapping it, so readers can route on `type` and redeliveries dedupe on source + id.
- **`schedule` and `loopway` sources stay.** `schedule` still fills the inbox on a clock, and `loopway` is authenticated push.
- **Read is one paginated endpoint.** All requests are authenticated as the user. A message drops out of the database 14 days after it arrives.
- **Cursors are microsecond timestamps.** Resetting a reader means picking a time, not guessing a number.
- **Delivery is at least once.** Readers can see a message twice, and dedupe on the CloudEvent id if that matters to them.

## The CLI

`loopway read <reader.js>` reads everything since the last read, and `loopway poll <reader.js>` keeps polling. Both call the reader once per message, in order:

```js
export default async function (msg, ctx) {
  // msg: the CloudEvent + received_at
  if (msg.type.startsWith("com.github.")) await handle(msg);
}
// resolves -> the cursor moves past msg
// throws   -> the run stops, and msg comes again next time
```

- The cursor is a file in `~/.loopway`, named by a hash of the read's arguments (the reader's path and the user).
- A reader with no cursor starts from now; `--since <time>` backfills or resets it.
- One login at a time: `~/.loopway/config.json` holds one user, and `LOOPWAY_API_KEY` overrides it per process.

## MCP

A hosted MCP endpoint on the server, with bearer auth, offers tools that push and pull messages. `pull` takes a `since` and returns the next one, so it keeps no state.

### Read cursors

- Postgres `timestamptz` holds microseconds, but JavaScript `Date` doesn't: `received_at` has to leave the database as text and travel as an integer or string, and `iso()` in `api.ts` truncates to milliseconds.
- Reads have to be inclusive of the cursor (`>=`): two messages can share a microsecond, and at-least-once allows the repeat.
- `received_at` is set when the insert starts, but a row only becomes visible when it commits, so a slower insert can appear behind a reader that has already read past it. The read must not hand out rows newer than a few seconds, or must re-read a few seconds behind the cursor. (The old routing did this: `ROUTE_HOLDBACK_SECONDS` in git history.)

## Moving over

- **Data:** migration `040_v2` keeps users and their usernames (which used to be the slug of a personal org) and drops orgs, inboxes, messages, bots, threads and runners. The Vercel build runs migrations, so merging to main applies it to production.
- **CLI:** the server's `MIN_CLI_VERSION_FLOOR` is 2.0.0, so every v1 CLI gets a `426` and updates itself.
- **Webhooks:** each sender's URL changes, so each secret is registered again.
- **plumbline:** `bin/plumb` and the five bots in `bots/` run on `loopway bots`, which is gone. They stop at the merge until they're rewritten as readers.
