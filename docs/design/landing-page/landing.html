A runner for bots

Bots that run your process, and ask when they need you.

loopway listens to the services you already use, keeps every event in an inbox, and hands them to bots running on your machines. A bot is a prompt and a few rules, run by the coding agent you pick: Claude Code, Codex, Cursor or Hermes. We build loopway with seven of them.

Levels of automation

From starting every piece of work to writing the rules it runs by

loopway records the level of every thread. One a person starts is level 2. One a bot starts is level 3 if a person takes part, and level 4 if no one does. The dashboard shows each bot's threads by level, so you can see the work move up.

  1. Level 1

    Assisted

    You ask a model, read the answer, and do the work yourself. Nothing for loopway to run.

    You start it. You do it.
  2. Level 2

    You start it

    A person opens the issue or sends the message, and a bot carries the work from there.

    You start it. A bot does it.
  3. Level 3

    A bot starts it, you take part

    A deploy, a schedule or another bot starts the work. The bot asks when it needs a decision, where you already are: a comment, a review, an issue.

    A bot starts it. You answer it.
  4. Level 4

    No one has to

    Bots start the work and finish it, handing it to each other. You read the results and change the rules, not the work.

    Bots start it. Bots finish it.

How it works

From an event to finished work

Each part keeps one fact and passes the rest along. Nothing is locked and nothing is marked done, so an event is never lost to a crash.

  1. 01

    Source

    deployment.error

    A service you use, a schedule, or another bot sends an event to the inbox. The inbox checks its signature.

  2. 02

    Inbox

    com.vercel.deployment

    Keeps each event as a CloudEvent, in the order it arrived. Messages are a record to read from, not a queue to drain.

  3. 03

    Bot

    prompt v2 · 3 rules

    Reads its inboxes with a cursor, so it picks up where it left off. Its rules decide which thread each event belongs to.

  4. 04

    Runner

    lease 30s · max 3

    Your machine, running loopway bots run. It leases each bot, so two runners never do the same work.

  5. 05

    Session

    claude · codex · cursor · hermes

    The bot's agent, started with its prompt. It does the job, asks when it needs to, and ends the thread when the work is done.

Threads

A thread is one piece of work and every event about it

Every later event for the same work lands in the same session, so the bot remembers what it already tried. When it needs you, it asks where you already work, and the next run reads your answer.

  • Rules match on event type and subject. A subject no thread holds starts a new one.
  • A thread ends when the bot says the work is done. Its next event wakes it.
  • You can write to a thread from the dashboard or the terminal, and every transcript stays on the runner that wrote it.
Runners

It runs on your machine, with your own agents

We host the inboxes and the threads. The sessions run where you start the runner, on the agent accounts you already pay for.

Leases

Each tick the runner renews its lease on every bot it holds. A second runner skips a held bot and says until when. Quit, crash or close the lid, and the lease is released or runs out.

A sandbox

Sessions can write to the checkout and the caches they need. Your SSH keys, cloud credentials and the rest of your home directory stay out of reach.

Usage limits

When an agent reports a usage limit, the runner stops delivering until it resets, then carries on. Events keep arriving and wait on their threads.

Versions

A bot's prompt and rules are saved together as a version. Running threads keep the version they started on.

Write your own

A bot is a prompt, its rules, and an agent to run them

Pick the agent and model, write the prompt, and add rules that say which events it takes and how they group into threads. Or skip the runner and read the inbox yourself: every read command in the CLI takes --json.

The HTTP API · The CLI

CLI
$ loopway inbox create --name vercel-prod --source vercel
$ loopway bots create --name deploys --harness codex --inbox vercel-prod
$ loopway bots run
HTTP
$ curl -H "Authorization: Bearer $TOKEN" \
    https://loopway.craftmill.dev/api/bots/$BOT/messages
Sources

Seven sources so far, and loopway is one of them

An inbox listens to one source. A bot can read several, so a failed deploy and the issue it caused can land in the same thread.

GitHub

source_type: "github"

Issues, comments, pull requests, reviews, pushes and CI, from a repository or an organization.

Linear

source_type: "linear"

A workspace's issues and the comments on them.

Vercel

source_type: "vercel"

A team's deployments, as they start, fail and finish.

Granola

source_type: "granola"

Meeting notes from a workspace or a folder.

Resend

source_type: "resend"

What happens to the email you send and receive: delivered, bounced, opened, clicked.

Schedule

source_type: "schedule"

A message each hour, or each day at an hour you pick, to wake a bot on a rhythm.

loopway

source_type: "loopway"

Messages posted straight to an inbox, so bots and backends can message each other.

Start with one inbox and one bot.

Log in with your email, point a webhook at an inbox, give a bot a prompt and its rules, and run loopway bots run. The next event is its first thread.
